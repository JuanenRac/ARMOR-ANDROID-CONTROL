# The mobile client's boundary

ARMOR-ANDROID-CONTROL consumes ARMOR-SERVER's API. It does not connect to cameras over RTSP, and it never receives the cameras' passwords, their RTSP paths or the key that encrypts the camera configuration.

## The current flow

1. The person enters an HTTPS origin, or an HTTP origin limited to a private LAN address (`10/8`, `172.16/12`, `192.168/16`, loopback), and signs in with the user and password Studio uses (`POST /api/v1/studio/session`). The server answers with an HttpOnly session cookie, which the app keeps sealed with a key of the Android Keystore; the password is kept only if the person ticks "Remember me" on the sign-in (off by default): then the user and the password are sealed with a separate Keystore key, for that one server, and forgotten the moment the box is unticked.
2. The role of the user decides what the app offers: an administrator may do everything (arm, disarm and silence the siren of the alarm panels included), an operator may change devices, cameras and alarms, and a viewer (or the wall-panel role) only looks. The server enforces the same roles; the app just does not offer what would be refused.
3. The client reads `status`, `camera-views`, the alarms, the devices and the rest, read-only. PTZ, snapshots, recording and the evidence catalogue need an operator.
4. Video uses ARMOR-SERVER's MJPEG relay, opened with a stream ticket the server gives to every role (a viewer cannot watch without one). The phone never builds an RTSP URL and so it cannot reveal a camera password.
5. The app can ask for the lock of the phone itself (fingerprint, face, or the PIN, pattern or password of the phone) before arming, disarming, silencing a siren, unlocking and the other critical orders, and, if the person turns it on, to open the app. The person's switches decide; the server's security option `client.device_lock` (announced in `capabilities.security` of the session) can only raise them, and a phone with no screen lock is never asked for anything. The check is made by the phone and protects an unattended phone: the server keeps checking the session, the PIN and the proof of identity by itself, so a modified client gains nothing from skipping it. The locked screen always offers signing in again with the password, which forgets the session kept on the phone. The background watch for alarms and their notifications are not behind the lock.
6. The alarm of a duress PIN (the PIN a person types when forced to disarm) is never announced, spoken, listed or counted by the app: the server tells the people who must know in silence.

## Deliberate limits

- Arming, disarming and silencing a siren need an on-screen confirmation and a signed-in session; the server records it with the user's name. Acknowledging an alarm does not close it: it closes by itself when its cause ends.
- HTTP is allowed only for a current home/LAN installation. Exposure outside that network must terminate TLS before the APK is distributed.
- **Updates.** On every cold start the app asks GitHub's releases for a newer stable version (`vMAJOR.MINOR.PATCH`) and, if there is one, offers it; the APK is the release's own asset, named exactly `ARMOR-ANDROID-CONTROL-release.apk`, and it is handed to Android's installer, which checks its signature before replacing the app. Nothing is downloaded or installed without an explicit tap. A release carries a `versionCode` higher than the previous one. The APK is signed with the maintainer's own release key, kept outside the repository: Android accepts an update only when it is signed with the same certificate as the installed app. The app checks the package name, the size, the `versionCode` and the signing certificate (it must share one with the installed app, a rotated key included) before it hands the file to the installer, and says so in plain words when the key is another one.

## Setting up a field node over Bluetooth

For a node with no Ethernet cable, or no address yet, the app configures it over Bluetooth Low Energy with the same protocol as its web panel (`docs/BLE_PROVISIONING.md` of ARMOR-NODE-RADAR, ARMOR-NODE-SOLAR, ARMOR-NODE-ELECTRICAL, ARMOR-NODE-ALARM and ARMOR-NODE-HMI: the five kinds of node speak the same protocol and the app says which one it is). It looks for the nodes that advertise `ARMOR-xxxxxx`, connects, creates the administrator of a new node with its set-up code (or signs in), searches for Wi-Fi networks, sets the name, the connection (cable or the Wi-Fi of a router), DHCP or a fixed address (address, mask, gateway, DNS) on either connection, the broker and the Bluetooth mode, and restarts the node.

- **The outcome is read back.** After the restart the app looks for the node again over Bluetooth and reads its `hello`: whether it joined (its address and network) or why it did not (network not found, wrong password, or only "it did not connect"), with buttons to check again or to change the configuration. A node set up to join a Wi-Fi network keeps advertising until it has an address. This needs the node firmware that reports `sta_error`; with an older one the app says only that it cannot tell.
- **The form is checked before it is sent:** a Wi-Fi name is needed, a Wi-Fi password has 8 to 63 characters, and a fixed address, mask and gateway must be valid and in the same network.
- Permissions: `BLUETOOTH_SCAN` (declared as not used for location) and `BLUETOOTH_CONNECT`; location is asked for only up to Android 11, where scanning requires it.
- The link is encrypted and authenticated: Android asks for the six-digit PIN the node prints on its USB console (an administrator can also read it in the node's panel), so someone listening in, or present while the phone pairs, cannot take part. The PIN does not change from one pairing to the next, so the node's set-up code (it derives the PIN) must stay private. The administrator password and the set-up code travel inside that link.
- The app does not store the code, the fleet secret or the passwords.
- **Verification:** the protocol's format, its operations, the set-up code calculation, the form checks and the reading of the outcome have JVM tests, but the flow has not been run end to end against a node and a phone by the tests; pairing, the MTU and reconnecting are the first things to check on the bench.
